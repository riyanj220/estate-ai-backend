# Stories 5.14 and 5.15: resume, idempotent turns and graceful degradation

Sources: `epics.md` Epic 5, FR-29, FR-31, AD-8, AD-25. Builds on spec-5-8 and spec-5-11-to-5-13. No new route, table or field.

## 5.14

- Everything is saved as it happens, so "save" is leaving. Opening the Draft's session again returns the same id, its answered turns, and `summary` and `next_step` computed from the Draft now.
- A repeat of an answered `client_turn_id` returns the stored turn and the `message` it was first answered with (now stored in `result`), with no model call and no write. `next_step` and `summary` are current, not historical. Another message under the same id is `422`.
- A failed turn stores nothing, so its repeat is processed. A repeat while the first is still running is `409`; the client keeps the id.
- Description generation gets no key: it is not a turn. A repeat is `409 stale_revision` and the review page shows the saved text.

## 5.15

- Provider down or rate-limited: `error`. Slow: `timeout` (also when the adapter's own socket gives up). Flag off: `fallback`. Budget used up: `budget_exhausted`. All are `200` with a message, no turn and no Draft change. The account's own limit stays `429`.
- The 20 s bound is per model call. Retrieval has its own 12 s; when it fails or is slow the turn is answered without sources, so a whole turn can take about 32 s.
- The manual flow uses no AI call.
- Frontend: a failed message or description keeps what was typed and says how to continue by hand. Plain UI; polish deferred.

## Checks and limits

`tests/assistant/test_resilience.py` (fault injection against the stub), frontend `tests/e2e/assistant-resilience.spec.ts`. A reload while a turn is in flight does not show it until the next load. A timed-out call keeps its worker until the adapter returns.
