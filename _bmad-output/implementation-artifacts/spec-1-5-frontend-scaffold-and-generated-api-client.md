## Intent

**Problem:** There is no frontend, so nothing consumes the backend contract, and `openapi.yaml` is still empty because the health endpoint is a plain Django view outside the schema.

**Approach:** Scaffold the Next.js frontend in its own repository (`/home/riyan/Riyan/projects/estate-ai-frontend`, branch `story/1-5-frontend-scaffold-and-generated-api-client`) with a same-origin `/api` proxy, one sync script generating a committed typed client from the backend `openapi.yaml`, a health page that calls the backend through that client, and lint, type check, Playwright and axe tooling with CI. In the backend repo, make the health endpoint part of the contract first.

## Boundaries & Constraints

**Always:** two repositories, two git histories; frontend uses npm, an exact Node version pinned in `.nvmrc` and `package.json` `engines` (Node 24), and a committed `package-lock.json`; Next.js 16 App Router with TypeScript strict and Tailwind; route groups `(public)`, `(app)` for signed-in pages and `admin`, each holding only a placeholder page; the browser only calls `/api/*` on its own origin, proxied by Next.js to `BACKEND_URL` (default `http://127.0.0.1:8000`); the typed client is generated by one script from the backend `openapi.yaml` into a committed directory that is never hand-edited and carries a header saying so; the committed spec copy lives in the frontend repo so CI can regenerate and diff without the backend; the health page is a server component that forwards the incoming cookie; no visibility, privacy or quota logic in the frontend; no secrets committed; backend health keeps its behaviour (`200 {"status":"ok"}`, `503 {"status":"unavailable"}`, GET and HEAD) and the Story 1.3 error envelope for everything else; backend tests, ruff, import contracts and the `openapi.yaml` freshness test keep passing.

**Never:** build UX, design system, auth, forms or any business screen (no UX contract exists; `bmad-ux` runs before Story 1.15); hand-write API types; add a state or data-fetching framework beyond what the scaffold needs; call the backend directly from the browser; change backend behaviour other than moving health into the contract.

## Design Notes

Decisions made without asking: Node 24 (installed LTS); `openapi-typescript` plus `openapi-fetch` for a small typed client; the spec copy is committed in the frontend repo so CI can regenerate offline and compare with the backend `main` raw file as the staleness check; health moves into DRF in the backend because the contract must contain the endpoint the frontend calls (the Story 1.3 note that health stays plain is superseded here); planning documents and this spec stay in the backend repo; the frontend repo has no BMAD tooling.
