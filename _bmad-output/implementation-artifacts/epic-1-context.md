# Epic 1 Context: Accounts and Secure Access

## Goal

Visitors can register Individual or Agency accounts, verify email, sign in, reset passwords and manage profiles; administrators are provisioned (never self-registered) and use a protected admin area; account states, notifications and audit capture work. The epic also scaffolds the Django backend and the Next.js frontend, the local environment, and the CI gates that enforce the architecture, so every later epic builds on a secure, reproducible base. Profile picture and Agency logo uploads are completed in Epic 2.

## Requirements & Constraints

- Individual registration: full name, email, password (min 8, not commonly used) and phone (Pakistani mobile or international) all mandatory; no buyer/seller role choice. Agency registration uses a separate form: agency name, business email, business phone, office address, city (from the City list) and credentials.
- Email is case-insensitively unique; a duplicate registration or reset request must be indistinguishable from a new one (no existence disclosure; the existing address gets a notice). Phone numbers need not be unique and duplicates are never reported.
- Email verification links are single-use and expire in 24 hours; password reset links are single-use and expire in 1 hour. Email change requires verifying the new address first.
- Sign-in errors are generic; 5 failed attempts in 15 minutes throttles automatically. A new session is issued at every sign-in; sessions end on sign-out, password change/reset and deactivation.
- Account states: Email-unverified, Active, Suspended, Deactivated, derived from separate conditions. Suspended accounts can sign in (see reason, restricted actions refused); Deactivated cannot sign in and sessions end immediately. Reactivation returns to Active only if email is verified. Capabilities that depend on later features are marked pending and each later story activates its own cell.
- Administrators: provisioned by command only (audited, no default credentials, no registration path); all admin routes require the Administrator capability; strong password policy; sessions expire after 30 minutes idle or 8 hours; password reset only via the provisioning command; cannot own Listings.
- Privacy: phone, email, private address are private-class, never in public responses, logs, error bodies or audit metadata; Agency business phone and full address are private, name/description/city public. Agency name/description reject contact details.
- Notifications: in-app list (newest first, cursor-paginated, read/unread); stored after commit only. New Messages are not notifications; no email alerts for offline recipients.
- Rate limits (NFR-10 defaults): registration 10/hour per client; verification and reset emails 5/hour per account; all NFR-10 rows seeded in the policy table, each applied by the owning story. 429 uses the standard error envelope with a retry hint.
- Agency employees are not distinguished (no per-employee seats).

## Technical Decisions

- Stack: Python 3.12, Django 5.2 LTS, DRF, drf-spectacular, Channels with Daphne, PostgreSQL 18 + pgvector (Docker Compose, plus a dev mail catcher, both on 127.0.0.1), import-linter, uv, Next.js 16 App Router with Tailwind, Playwright and axe. Dependencies locked with hashes and audited.
- Two repositories (backend, frontend); contract is the committed `openapi.yaml`, CI fails if stale; the frontend's typed client is generated by one sync script, committed, never hand-edited. [BE+FE] stories run backend first, then frontend. No visibility, privacy or quota logic in the frontend; Next.js proxies `/api/*` to Django (one origin).
- Layered apps under `apps/` (bottom to top): `kernel`, `catalog`, `identity`, `listings`, tier-4 (`valuation`, `search`, `assistant`, `messaging`), `governance`, `presentation/{api,adminapi,realtime}`. Each domain app exposes `services`, `selectors`, `events`. Imports go downward only; tier-4 peers never import each other; no app imports another's `models`; only the owner writes its tables; serializers are explicit allowlists (`fields = "__all__"` banned). Enforced by import-linter contracts proven with failing fixtures. Kernel tables hold account ids as plain UUIDs without foreign keys.
- Database hosting (A12): Docker PostgreSQL + pgvector for local and CI; Supabase PostgreSQL as the hosted database (plain PostgreSQL only). Django migrations are the sole schema authority; roles created by SQL on Supabase; migrations use the direct connection.
- Settings split base/local/test/prod via env vars; prod refuses missing or default secrets; secret scan in CI. Separate migration and runtime DB roles (runtime has no DDL). Daphne one process, one worker; synchronous views were assumed to share one thread under ASGI; the Story 1.2 spike refuted this (see `docs/architecture-notes.md`), so AD-14 needs amendment before the messaging epic; sign-in/session endpoints stay async or DB-only.
- Security baseline: explicit `ALLOWED_HOSTS` and trusted origins (no wildcard); HttpOnly, SameSite=Lax, Secure (outside local) session cookies with CSRF; security headers and CSP; links built from `FRONTEND_BASE_URL`, never Host; Django admin absent outside local; forwarded headers trusted only from a configured proxy list.
- Errors: `{error:{code,message,fields,request_id}}` with a stable code catalogue in the schema (409 stale revision, 422 `idempotency_key_reused`, 429 throttled); cursor pagination; structured JSON logs with `request_id` and an allow-list of fields (global middleware test).
- Authorisation: every request resolves to an `Actor` (visitor, user, admin, system); services take `actor` first and enforce policy themselves, never reading ambient request state; DRF default is deny and a route-permission test fails any route without an explicit declaration; unauthorised resource access returns not-found, sign-in-required returns unauthenticated; a documented authorisation matrix is extended by later phases.
- Kernel primitives built here: rate-limit policy table persisted in PostgreSQL (client key = account, or trusted-proxy address plus session for Visitors); event bus using `transaction.on_commit(robust=True)`, one callback per subscriber, subscribers registered in `AppConfig.ready`, failures logged and never affecting the response; idempotency via `kernel.idempotency.claim(scope, account_id, key, request_hash)` (per account, 24 h honoured, purged after 7 days, result reference only); bounded runtime executor with capacity reserved for chat and sign-in; feature-flag store (name, state, who, when); AI request log (no content); `run_retention [--dry-run]` with app-registered purge hooks; mail port sending after commit via the event bus; shared contact patterns in `kernel.privacy.patterns` (phone, email, address, with a false-positive set) and `reject_contact_details(text)`, the only contact regex in the repo.
- Audit: written in the same transaction as the action, plain UUID refs, allow-listed metadata, append-only for the runtime DB role (UPDATE/DELETE refused). Private reads go through `kernel.privacy.record_private_read(actor, reason, target_ref)` (fail closed; POST-only with a reason; closed target enum; enumeration test).
- Identity owns the Account model (case-insensitive unique email, password hash, verified/suspended/deactivated conditions), `identity.can(actor, capability)` for the capability matrix, `lock_account(account_id)` and `is_active_owner` as the only lock/eligibility primitives; emits `account.session_ended` on sign-out, password change and deactivation. Every state change is audited. Catalog owns City (seeded with Karachi, served at `/api/v1/reference/cities`; reference values are DB-managed strings, never OpenAPI enums).
- Conventions: snake_case keys, UUID primary keys, UTC ISO 8601 timestamps, events named `domain.past_tense`, URLs plural nouns under `/api/v1/`.

## UX & Interaction Patterns

- No UX design contract exists yet; run `bmad-ux` before the first user-facing frontend story (Story 1.15). Frontend stories carry behaviour only and flag where a design decision is needed.
- Forms show field-level errors, the rate-limit message and a success state; Individual and Agency registration are separate pages.
- Verification result page covers success and each failure (expired, used) with a request-new-link option.
- Layout reflects signed-in state; CSRF handled through the proxy.
- Admin route group redirects Visitors and non-admins to admin sign-in; the shell shows an empty dashboard with navigation placeholders and passes the axe check.
- Notifications page shows the list and unread count.
