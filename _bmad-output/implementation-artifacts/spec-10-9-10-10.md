# Stories 10.9 and 10.10: support requests and the administrator second factor (BE+FE)

Acceptance criteria: `epics.md`, Epic 10. Rules: FR-10, FR-71. Owner direction: a final-year project; plain screens
(the UI is redesigned later). Constraints: `docs/story-checklist.md`.

## API (never cached)

| Route | Meaning |
|---|---|
| `GET, POST /api/v1/me/support-requests` | own latest 20; submit `{category, message}` |
| `GET /api/v1/me/support-requests/{id}` | one of the caller's own |
| `GET /api/v1/admin/support-requests?status&cursor` | queue without message text |
| `POST /api/v1/admin/support-requests/{id}/read` `{reason}` | the message (reasoned read `support_request`) |
| `POST /api/v1/admin/support-requests/{id}/close` | close and notify (`support.closed`) |
| `GET /api/v1/admin/second-factor` | `{enrolled}` |
| `POST /api/v1/admin/second-factor/enrolment` `{password}` | pending secret and `otpauth://` URI |
| `POST /api/v1/admin/second-factor/confirm` `{code}` | turn it on |
| `POST /api/v1/admin-session` `{email, password, code?}` | `code` needed once enrolled |

Screens: `/account/support` (linked from the profile page), `/admin/support`, `/admin/second-factor`, and an optional
code field on the administrator sign-in.

## Decisions

- Support: `governance.SupportRequest` with category (`account`, `decision`, `technical`, `other`) and a 10 to 2000
  character message, so the queue is usable without reading text. The existing `support_requests` policy (5 a day) is
  used. Closing carries no reply text. The message may contain contact details (it is private).
- Account closure empties the messages and closes open requests; rows stay for retention (10.12).
- Second factor: stdlib RFC 6238 (no OTP library), Fernet encryption (`cryptography`, already locked as a transitive
  dependency, now direct) with a key derived from `DJANGO_SECRET_KEY`: no new setting.
- Optional enrolment. A missing, wrong or replayed code is the same generic 401 as a wrong password and counts in the
  existing administrator sign-in throttles. New policy `admin_second_factor` throttles enrolment attempts.
- Enrolment asks the password again; confirming ends the other sessions. No web route turns it off:
  `provision_admin reset-second-factor`. A password reset keeps the second factor.
- Recorded: enrolled, used, failed, reset. Starting an enrolment (nothing active yet) is not recorded.
- No QR code and no outside service: the key and URI are shown once.

Details: `docs/administrators.md`, `docs/account-states.md`, `docs/rate-limits.md`.
