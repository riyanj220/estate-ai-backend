## Findings

Each finding carries its source and disposition (fix now / defer / accept).

### Aggregate views

1. **God-module growth: `apps/identity/services.py` is 1,379 lines with 66 top-level definitions** (`wc -l`, `grep -c "^def \|^class "`), the next largest application file is 304 lines (`apps/kernel/notifications.py`). Stories 1.15 to 1.22 each added a service area (registration, verification, sessions, password reset, profile, email change, agency, admin provisioning) to the same module. Disposition: **fix now (before Epic 2)**, action item 1.
2. **Architecture delta is clean**: the layering contract set (13 import-linter contracts) passed on every story; the only structural decisions that needed a documented exception were the notification service placed in the kernel (spec 1-24) and management commands under identity (spec 1-22). No presentation to identity-model imports (`grep`: none). Disposition: **accept**.
3. **Duplication**: the frontend repeats form scaffolding (error summary, notice, announcement, 400 handling) across at least five forms; extraction happened once (Story 1.19: `form-field`, `error-summary`, `use-form-feedback`) but the Individual register form never adopted the agency form's error handling, and the notification list stretched `useProfileLoad` (blind review of Story 1.24, spec 1-24 frontend triage; Story 1.19 and 1.20 triage deferrals). Disposition: **defer**, action item 5.
4. **Pattern divergence**: none found in the backend; the three-review loop plus the actor-first service convention held across all 24 stories. Frontend divergence is limited to the Individual register form (above). Disposition: **accept**.
5. **Spec-to-implementation reconciliation** (as-built differs from the written contract; each is an accepted deviation to record in the project contract, action item 9):
   - Story 1.17 AC "5 failed sign-ins within 15 minutes for one account and address": implemented per (email, client network), plus (Story 1.22) a per-account ceiling for administrators only (spec 1-17 and 1-22 triage).
   - Story 1.18 AC "reset emails exceed 5 per hour per account returns the 429 envelope": a per-account 429 would reveal that an address exists, so the 429 is per client and the per-account cap is silent (spec 1-18, `docs/password-reset.md`).
   - Story 1.20: `pending_email` semantics changed after the first merge (`fix(identity): show the pending email for every accepted change request`, commit `a8584c1`) because showing it only for issued links was an enumeration oracle.
   - Story 1.23 spec: the "administrator already signed in at the ordinary page" and password-page chrome behaviours were added during review (spec 1-23 triage).
   - Notification ordering: a late-committing row can carry a lower sequence number than one already visible (documented in `docs/notifications.md`, spec 1-24 triage).

### Lens findings

6. **Enumeration and side-channel defects recurred in four stories** even though each spec stated the rule: Story 1.18 (known versus unknown address did different response-path work), Story 1.20 twice (the heads-up mail only on the free-address branch; `pending_email` only for issued links), Story 1.22 (throttled attempts skipped the hash; failure audit write only for existing administrators, plus a speed oracle). All were caught pre-merge by the blind or edge-case reviewer, none shipped, but they were found late each time. Disposition: **fix process now**, action item 2.
7. **Security defects found by reviewers before merge** (each with its triage row): token link surviving a password change (1.20), distributed brute force of one administrator (1.22), email-change confirm accepting administrators (1.22), disable guard and race for the last administrator (1.22), admin dashboard restorable from the back/forward cache after sign-out (1.23), admin door distinguishable by 403 and 429 wording (1.23), a tampered pagination cursor causing a 500 (1.24), the emailed token restored in router `history.state` on three pages (1.20). All **fixed**. This is the strongest evidence that the three-reviewer loop earns its cost.
8. **Verification gaps** found repeatedly at the same boundary: assertions made before the triggering request settled (1.19, 1.21, 1.23) and tests that cannot fail under dev mode (no-store, prerender, 1.20 and 1.23). Mitigated by the production-build check `npm run check:prod-admin` (1.23); the same pattern should be applied to the `/reset-password` and `/confirm-email-change` static-page checks, which still rely on a documented manual curl step. Disposition: **defer**, action item 6.
9. **Test flakiness**: `tests/e2e/agency-profile.spec.ts` (a serial file from Story 1.21) failed once in each of three full runs, on a different cities test each time, and passes in full when run alone (82 of 82; sources: Playwright logs from the 1.23 and 1.24 verification runs). Serial mode then skips the rest of the file, which hides 60+ tests behind one flake. Disposition: **fix now**, action item 4.
10. **Secret-scan false positives three times** (stories 1.18, 1.19 and 1.20: gitleaks `generic-api-key` on fixture passwords). Handled by per-fingerprint entries in `.gitleaksignore` after explicit user approval each time (the auto-mode permission check blocked the second one). Disposition: **fix process**, action item 3 (a path-scoped allowlist decision).
11. **CI reading errors**: in Story 1.17 a stale run looked green while HEAD was red (fixed by comparing the run's `headSha` to HEAD), and `gh` network timeouts were reported as failures; the discipline is recorded in the memory handoff. Disposition: **accept** (process already adjusted).
12. **Dev environment drift**: running the real stack for the behaviour check applied kernel migrations 0008 to 0010 on the dev database, so the dev database had been lagging for several stories because tests use their own database. Source: `manage.py migrate` output during this retro. Disposition: **fix now**, action item 8.
13. **Commit history hygiene**: some intermediate commits do not build on their own (Story 1.23 removed the old admin placeholder page only in the last commit, leaving two pages at `/admin` in between). Final HEAD builds and CI is green. Disposition: **accept**; note for later stories: commit deletions with the replacement.
14. **Known security residuals, documented and deferred on purpose**: administrators and ordinary users share the `estate_session` cookie (a sign-in on one ends the other); the shared contact-detail patterns miss obfuscated phones and some address forms (`docs/privacy-patterns.md`); no operator identity in administrator audit records (accountability relies on OS and SSH logs); no per-account throttle on ordinary sign-in; agency-name uniqueness and lookalike names. Disposition: **defer**, action item 7.

## Behavior verification

Exercised the real backend (Django `runserver` on 127.0.0.1:8100 against the dev PostgreSQL and the local mail catcher) through the real Next.js proxy (`next dev` on 127.0.0.1:3300 with `BACKEND_URL` set), using `curl` with a cookie jar. Observed:

- Registration returned the generic `202 check_your_email`; the verification email arrived in the mail catcher; confirming its token returned `verified`.
- Sign-in without a CSRF token: `403 forbidden`; with the token fetched from `/api/v1/csrf`: `200` with the actor summary and an `HttpOnly` session cookie; the CSRF token rotated after sign-in.
- `GET /me/profile` returned the owner's phone in E.164; `PATCH /me/profile` changed the name; `POST /me/password` returned `200` and the notification list then held an unread `account.password_changed` item.
- Visitors and an ordinary-account cookie were redirected from `/admin` to `/admin/sign-in?next=%2Fadmin` and from `/dashboard` to `/sign-in?next=%2Fdashboard`; `GET /api/v1/admin/me` as an ordinary user was `404`.
- Sign-out returned `204` and `/me` was then `401`.
- Administrator path: `provision_admin create --password-stdin` created the account; a password on the command line and a weak password were both refused; the administrator's credentials failed at the ordinary door with the generic 401 and succeeded at `/api/v1/admin-session`; `/api/v1/admin/me` and the `/admin` page worked for the administrator; a public password reset request for the administrator returned the same `202` and sent no mail; `provision_admin remove --force-last` removed it.
- Not exercised in the real stack: Agency registration, email change, password reset through the emailed link, session expiry timings (covered by unit tests with a controlled clock) and the frontend pages in a browser (covered by the 667 Playwright tests against a stub backend, which is the residual contract-drift risk behind action item 6). A test individual account (`retro.check.*@example.test`) remains in the local development database.
